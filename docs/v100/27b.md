## 实测数据

### 2.0.1 实测数据（与 2.0.0 同场交替）

测试条件：IBM AC922（2 × POWER9，主机内存 96 GB）+ 6 × Tesla V100-SXM2-16GB；Qwen3.8-27B Q8_0 + DFlash2 F16，6 卡张量并行，上下文 262144。2.0.1 与 2.0.0 在同一时段交替测量（同一台机器、同一批提示词、机器独占）；2.0.0 一列是 2.0.0 发布线构建的同场测量。27B 的三个请求在同一个服务里按“短提示 → 约 1.6 万 token（温度 0.8，表中未列）→ 约 20 万 token”的顺序执行，约 20 万 token 的提示词命中了前一请求留下的缓存前缀，实际处理 195048 个 token；**温度 0、不开思考**（1.6 万档除外）。

<sub>测试数据：2026-10-17，2.0.1 发布构建对 2.0.0 发布线构建，同一台机器、同一时段交替测量；表中 2.0.0 一列即该次同场测得。</sub>

| 用例 | 2.0.0 | 2.0.1 | 变化 |
|---|---|---|---|
| 约 20 万 token 预填充（tok/s） | 2073 | 2140 | +3% |
| 约 20 万 token 吐字（tok/s） | 126.4 | 128.9 | +2% |

## 编译

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
  -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=70 -DGGML_CUDA_FA=ON -DGGML_CUDA_GRAPHS=ON \
  -DGGML_CUDA_NCCL=ON -DNCCL_INCLUDE_DIR=/path/to/nccl/include -DNCCL_LIBRARY=/path/to/nccl/lib/libnccl.so.2
cmake --build build -j --target llama-server llama-quantize
```

多卡张量并行需要 NCCL，编译器用 GCC 12 或更新的版本。GitHub 上每次推送都会自动按 sm_70 编译检查；发布版本附带 x86_64 Linux 的预编译程序（CUDA 12，见 Releases 页面），POWER9 等其他平台按上面的命令自行编译。

## 启动参数

AC922 上用 `numactl --membind=0,8` 把主机内存限定在两个 CPU 节点（GPU 显存被上线成 NUMA 节点，不限定时页缓存可能占用显存；节点号用 `numactl --hardware` 查看，带 CPU 的节点就是主机内存节点，AC922 通常是 0 与 8；x86 机器不需要这一段），其他机器用 `numactl -H` 查看节点编号；普通 x86 服务器去掉这一段。各参数的作用与影响见最后一节的参数表。

### A. 6 卡，上下文 262144（本页实测所用）

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5 numactl --membind=0,8 ./build/bin/llama-server \
  -m ./models/Qwen3.8-27B-Q8_0.gguf -ngl 999 \
  --split-mode tensor --tensor-split 1,1,1,1,1,1 \
  -c 262144 -np 1 -fa on -ctk q8_0 -ctv q8_0 -b 2048 -ub 2048 \
  --model-draft ./models/Qwen3.8-27B-DFlash2-F16.gguf \
  --spec-type draft-dflash --spec-draft-n-max 7 \
  --host 127.0.0.1 --port 8080 --metrics
```

### B. 4 卡，上下文 262144

命令 A 改 `--tensor-split 1,1,1,1` 与 `CUDA_VISIBLE_DEVICES`：AC922 上用 `0,1,3,4`（两颗 CPU 各两张）；x86 写 `0,1,2,3` 并去掉 `numactl` 一段。其余不变。

### 在 A / B 的基础上改

- **上下文 524288（YaRN）**：`-c 524288`，并加 `--rope-scaling yarn --rope-scale 2 --yarn-orig-ctx 262144 --override-kv qwen35.context_length=int:524288`；YaRN 设置对所有长度都生效。
- **多路并发**：`-np N`，每路上下文 = `-c` ÷ N（例如 4 卡 `-c 262144 -np 2` 每路 131072；6 卡两路各 262144 用 524288 的设置加 `-np 2`）。提示词处理按顺序排队，后面几路的首字要等前面的处理完，全部完成的总时间与依次处理差不多；好处是先开始吐字的请求不会被后来的长提示词卡住。`--prefill-pace`（默认 30，0 或 100 为不限流）调大，后来请求的首字更快、正在吐字的请求更慢。单个 Agent 要开满长上下文时仍用 `-np 1`。
- **多模态**：加 `--mmproj ./models/mmproj-F16.gguf`，处理视频再加 `--video-ffmpeg-dir <ffmpeg 所在目录>`。请求走 OpenAI 兼容的 `/v1/chat/completions`：图片用 `image_url`，视频用 `input_video`（或 `video_url`，默认每秒取 4 帧），PDF 由客户端把每页渲染成图片发送。视觉模块默认按层分到主模型使用的全部 GPU；显存不够时用 `--no-mmproj-offload` 放 CPU（处理图片、视频会慢很多），或 `-mmdev <设备>` 只放一张卡。
- **其他卡数**：改 `CUDA_VISIBLE_DEVICES` 与 `--tensor-split`（几张卡写几个 1）；各卡数的最高上下文见“判断步骤”。
- **Q4 配置**：`-m ./models/Qwen3.8-27B-UD-Q4_K_M.gguf -ctk q4_0 -ctv q4_0`。2 卡只能用 Q4 配置（Q8_0 主模型放不下 2 张 16 GB 卡），2 卡开 262144 时草稿换 `./models/Qwen3.8-27B-DFlash2-Q4_K_M.gguf`。
- **采样**：模型卡推荐思考模式 temperature 1.0、top_p 0.95、top_k 20、min_p 0（`--temp 1.0 --top-p 0.95 --top-k 20 --min-p 0`）；非思考模式 temperature 0.7、top_p 0.8、top_k 20、presence_penalty 1.5（`--temp 0.7 --top-p 0.8 --top-k 20 --presence-penalty 1.5 --chat-template-kwargs '{"enable_thinking":false}'`）。加在命令末尾作为服务默认，请求里带的采样参数优先。`top_k ≤ 64` 且只用 top-k、top-p、min-p、temperature 与 repeat/presence/frequency penalties 时，在设备端取 top-k 候选（候选数 = `top_k` + penalty 窗口内的 token，上限 256）；DRY 等其他采样器或 `top_k` 更大时，在主机上对全词表采样。

## Docker

镜像只包含 sm_70（V100）代码，基于 CUDA 12.4.1，内含 NCCL、ffmpeg（视频输入）、numactl 和 `llama-quantize`；宿主机需要 NVIDIA 驱动 550 或更新。镜像发布在 GitHub Container Registry，同一个标签同时包含 linux/amd64（x86_64 + V100，用 NVIDIA Container Toolkit 的 `--gpus all`）与 linux/ppc64le（仅 IBM Power AC922，用 `.devops/v100-ac922-cdi.sh` 生成的 CDI 描述，`--device nvidia.com/gpu=all`），`docker pull` 时按宿主机架构自动选择。入口是 `llama-server`，镜像名之后的参数直接传给它（路径改成容器内的 `/models/...`）。

### C. Docker，6 卡，AC922（podman，`podman-docker` 提供同名的 `docker` 命令）

```bash
sudo dnf install -y podman podman-docker
sudo bash .devops/v100-ac922-cdi.sh        # 生成 /etc/cdi/nvidia.yaml，只需执行一次；驱动升级后重新执行
docker run -d --name llama-v100 --device nvidia.com/gpu=all --ipc=host --ulimit memlock=-1 \
  -e LLAMA_NUMA_MEMBIND=0,8 \
  -p 8080:8080 -v <模型目录>:/models \
  ghcr.io/1115714829/llama.cpp-v100:2.0.1 \
  -m /models/Qwen3.8-27B-Q8_0.gguf -ngl 999 \
  --split-mode tensor --tensor-split 1,1,1,1,1,1 \
  -c 262144 -np 1 -fa on -ctk q8_0 -ctv q8_0 -b 2048 -ub 2048 \
  --model-draft /models/Qwen3.8-27B-DFlash2-F16.gguf \
  --spec-type draft-dflash --spec-draft-n-max 7 \
  --port 8080
```

### D. Docker，4 卡，x86

```bash
docker run -d --name llama-v100 --gpus all --ipc=host --ulimit memlock=-1 \
  -p 8080:8080 -v <模型目录>:/models \
  ghcr.io/1115714829/llama.cpp-v100:2.0.1 \

  -c 262144 -np 1 -fa on -ctk q8_0 -ctv q8_0 -b 2048 -ub 2048 \

  --spec-type draft-dflash --spec-draft-n-max 7 \
  --port 8080
```

草稿模型转 F16 也可以用镜像里的 `llama-quantize`：

```bash
docker run --rm --entrypoint /app/llama-quantize -v <模型目录>:/models ghcr.io/1115714829/llama.cpp-v100:2.0.1 \
  /models/Qwen3.8-27B-DFlash2-BF16.gguf /models/Qwen3.8-27B-DFlash2-F16.gguf F16
```

- `<模型目录>` 写绝对路径；`--ipc=host`、`--ulimit memlock=-1` 是多卡通信需要的共享内存与锁页内存。只用部分 GPU 时，x86 写 `--gpus '"device=0,1"'`，AC922 写 `--device nvidia.com/gpu=0` 等；2 卡请用 Q4 配置。
- `-e LLAMA_NUMA_MEMBIND=<节点>` 让容器用 `numactl --membind=<节点>` 启动，只用于 AC922 这类把 GPU 显存上线为 NUMA 节点的机器（填有 CPU 的节点 `0,8`）；节点必须是 `numactl --hardware` 中存在的节点，否则容器启动即退出。不要用 `--cpuset-mems` 限定内存节点（会使容器内 CUDA 初始化失败）。
- 镜像默认设置 `LLAMA_ARG_HOST=0.0.0.0`，对外是否可访问由 `-p` 或 `--network host` 决定；对外服务时加 `--api-key-file /run/llama.apikey` 并挂载 `-v <密钥文件>:/run/llama.apikey:ro`。视频输入加 `--video-ffmpeg-dir /opt/tools/bin`（镜像内的 ffmpeg）。
- 不能访问 ghcr.io 时，从 Releases 页面下载镜像文件（`llama.cpp-v100-server-<版本>-<架构>.tar.gz`）用 `docker load -i <文件>` 导入，或在源码目录自行构建：`docker build -f .devops/v100-cuda.Dockerfile -t llama.cpp-v100:server .`。

## 快速部署（给 AI 助手与新手）

本页可以整页交给 AI 助手：按下面的判断步骤选命令 A～D（见“启动参数”与“Docker”），把模型路径换成实际目录，再按参数表与症状对照调整。表里的数字是 1.x 版本在标准测试机上的实测（27B 的功能与 1.1.1 相同，详见 [1.1.1 的 README](https://github.com/1115714829/llama.cpp-v100/blob/v100-1.1.1/README.md#测试数据)）。

### 参数表

“能力 / 速度 / 显存”三栏写的是把参数从推荐值改掉（或去掉）会怎样。

| 参数 | 作用 | 能力 | 速度 | 显存 | 推荐值 | 什么时候改 |
|---|---|---|---|---|---|---|
| `CUDA_VISIBLE_DEVICES`、`--tensor-split 1,…,1` | 选用哪几张 GPU；张量并行时各卡均分 | 卡数决定能用的配置与最高上下文（见判断步骤） | — | 卡越多，每卡占用越少 | 全部卡，几张卡写几个 1 | 换卡数时两处一起改 |
| `numactl --membind=<CPU 节点>` | 把主机内存限定在有 CPU 的 NUMA 节点 | — | — | AC922 上不加时，读模型产生的页缓存可能落进 GPU 显存节点，CUDA 回收不了，表现为显存不足 | AC922：`0,8`；x86：不加 | 在 AC922 这类显存并入系统内存的机器上一定要加 |
| `-m` | 主模型 | Q8_0（约 29 GB）或 UD-Q4_K_M（约 16.5 GB，Q4 配置） | Q4 配置的吐字比 Q8 慢 | Q4 省显存：2 卡只能用 Q4；3、4 卡用 Q4 可以开到 524288 | Q8_0 | 卡少或要更长上下文时换 Q4 配置（同时 `-ctk q4_0 -ctv q4_0`） |
| `-md`（`--model-draft`） | DFlash2 草稿模型 | 草稿只提议，输出由目标模型决定 | 短任务 F16 接受率更高（4 卡每轮产出 F16 3.23、Q8_0 2.76、Q4_K_M 2.84 token），长上下文三者相近 | 4 卡每卡峰值 F16 13.3、Q8_0 12.9、Q4_K_M 12.6 GB | F16 | 显存紧时换 Q4_K_M；2 卡 Q4 开 262144 必须换 |
| `--spec-type draft-dflash`、`--spec-draft-n-max 7` | DFlash2 投机解码，每轮最多起草 7 个 | 草稿只提议，输出由目标模型决定 | 提高吐字 | 草稿模型与草稿上下文占显存 | 开；7 | 不改 |
| `--spec-draft-ubatch`、`--spec-draft-sampling`、`--spec-draft-window` | 草稿上下文的物理批大小（默认继承 `-ub`）；起草方式（默认 `greedy` 取概率最大的 token，`probabilistic` 按概率起草、目标模型做拒绝采样）；MTP 草稿的窗口（DFlash2 用不到） | 两种起草方式的输出都服从目标模型按请求参数的采样 | — | — | 不写 | 不改 |

### 判断步骤

```text
第 1 步：有几张 16 GB 的 V100？（最高上下文为 1.x 实测）
  6 张          → 命令 A；Q8 最高 524288（加 YaRN）
  5 张          → 命令 A 改成 CUDA_VISIBLE_DEVICES=0,1,2,3,4、--tensor-split 1,1,1,1,1；Q8 最高 524288
  4 张          → 命令 B；Q8 最高 262144；Q4 配置最高 524288
  3 张          → 命令 B 改成 3 张卡；Q8 最高 131072（-c 131072）；Q4 配置最高 524288
  2 张          → 只能用 Q4 配置（Q8_0 主模型约 29 GB，放不下）；262144 时草稿换 DFlash2 Q4_K_M，F16 草稿最高 131072
  32 GB 的卡    → 没有测过；从同样卡数的命令起步
第 2 步：要处理图片、PDF 或视频吗？
  要            → 加 --mmproj（视频再加 --video-ffmpeg-dir）；显存不够时 --no-mmproj-offload（处理图片、视频慢很多）
  不要          → 不加
第 3 步：要超过 262144 的上下文吗？
  要            → -c 524288 并加 YaRN 那四个参数（没有测 262144 以上的输出质量）
  不要          → -c 262144 或更小
第 4 步：多个客户端同时用吗？
  是            → -np N，每路上下文 = -c ÷ N；单个 Agent 要开满长上下文时仍用 -np 1
  否            → -np 1
第 5 步：是 IBM AC922（GPU 显存并入系统内存）吗？
  是            → 命令前加 numactl --membind=<CPU 节点>（一般 0,8）；用 Docker 时用命令 C（-e LLAMA_NUMA_MEMBIND=0,8）
  否            → 不加 numactl，也不设 LLAMA_NUMA_MEMBIND；用 Docker 时用命令 D
第 6 步：显存紧张、启动失败？
  依次试        → -c 调小 → 草稿换 Q4_K_M → 换 Q4 配置（-m UD-Q4_K_M，-ctk q4_0 -ctv q4_0）
```

### 症状与处理

| 症状 | 先查 | 处理 |
|---|---|---|
| 启动时显存不足 | AC922：页缓存是否落进了 GPU 显存节点（见最后一行）；GPU 上有没有其他进程；卡数与上下文是否超出判断步骤第 1 步的上限 | `-c` 调小；草稿换 Q4_K_M；换 Q4 配置；`-ub` 保持 2048；视觉模块显存不够时用 `--no-mmproj-offload` 或 `-mmdev` |
| 吐字慢 | 采样设置（`top_k` 是否大于 64、是否用了 DRY 等）；温度；是否多路 | `top_k ≤ 64` 且只用 top-k、top-p、min-p、temperature 与 penalties 时在设备端采样；温度大于 0 时接受率本来就低；多路时每路吐字本来就低于单路，`--prefill-pace` 调小可以让正在吐字的请求更快 |
| 多路时后来的请求首字慢 | — | 提示词处理按顺序排队，后面几路的首字要等前面的处理完；`--prefill-pace` 调大，后来的请求首字更快 |
| 草稿接受率低 | 温度；草稿量化；上下文长度 | 短任务用 F16 草稿接受率更高；长上下文每轮产出本来就少（4 卡 F16：短任务 3.23、128K 2.46 token / 轮） |
| 图片 / 视频请求报错 | `--mmproj` 是否加了；视频是否找得到 ffmpeg；PDF 是否先转成了图片 | 加 `--mmproj`；视频加 `--video-ffmpeg-dir`；PDF 由客户端把每页渲染成图片再发；`-c 1048576 -np 2` 时处理图片的计算缓冲分配不到显存，改用 `--no-mmproj-offload` |
| 日志里有 `llama_params_fit is not implemented for SPLIT_MODE_TENSOR` | — | 这是警告：张量切分不经过启动时的显存规划，按命令里的参数启动，可以忽略 |
| AC922 上显存被莫名占用、加载模型后显存不足 | `numactl --hardware` 里没有 CPU 的节点就是 GPU 显存，看它们的 free 是否变小 | 用 `numactl --membind=0,8` 启动；下载、复制大文件也用它包起来；已经落进去的页缓存用 root 执行 `sync; echo 1 > /proc/sys/vm/drop_caches` 清掉 |
