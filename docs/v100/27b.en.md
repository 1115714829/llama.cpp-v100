## Measured results

### 2.0.1 measured results (alternated with 2.0.0 in the same window)

Conditions: IBM AC922 (2 × POWER9, 96 GB of host memory) + 6 × Tesla V100-SXM2-16GB; Qwen3.8-27B Q8_0 with DFlash2 F16, 6 GPUs with tensor parallelism, context 262144. 2.0.1 and 2.0.0 were measured alternately in the same time window (same machine, same set of prompts, machine dedicated); the 2.0.0 column is a same-window measurement of the 2.0.0 release-line build. The three 27B requests ran in one server in the order "short prompt → about 16K tokens (temperature 0.8, not listed in the table) → about 200K tokens"; the ~200K-token prompt hit the cached prefix left by the previous request, so 195048 tokens were actually processed; **temperature 0, thinking off** (except the 16K case).

| Case | 2.0.0 | 2.0.1 | Change |
|---|---|---|---|
| Prefill, about 200K tokens (tok/s) | 2073 | 2140 | +3% |
| Decode, about 200K tokens (tok/s) | 126.4 | 128.9 | +2% |
| Decode time per round, about 200K tokens (ms) | 26.22 | 25.96 | −1% |
| Decode, short prompt (tok/s) | 216.0 | 225.8 | +5% |

For the short prompt, accepted tokens per round are bit-identical between 2.0.0 and 2.0.1; at about 200K tokens the output of 2.0.0 differed between its two rounds (accepted 712/2205 and 718/2163), while 2.0.1 gave the same output in both rounds (718/2142) — the non-reproducible T=0 output of 2.0.0 across restarts on 6 GPUs at long context is fixed in this version.

VRAM peak per GPU (highest of all GPUs, MiB):

| Case | 2.0.0 | 2.0.1 |
|---|---|---|
| 27B | 9969 | 9963 |

The draft model is only published as BF16, Q8_0 and Q4_K_M GGUF; the recommended F16 (V100 has no BF16 hardware support) must be converted once with the `llama-quantize` built from this project. Build first (next section), then download and convert with one command:

```bash
scripts/v100-get-models.sh            # downloads from ModelScope to ./models by default
scripts/v100-get-models.sh -s hf      # use Hugging Face instead
```

The script downloads the target and draft models (resumable; files already present are skipped), then converts the draft to `Qwen3.8-27B-DFlash2-F16.gguf`; `-d` sets the model directory, `-q` the path to `llama-quantize`, `-h` shows usage. The vision module is not in the script; download it separately when needed. If you already have the files, only convert: `./build/bin/llama-quantize Qwen3.8-27B-DFlash2-BF16.gguf Qwen3.8-27B-DFlash2-F16.gguf F16`. Single files can also be fetched resumably from a ModelScope direct link: `wget -c https://modelscope.cn/models/<repo>/resolve/master/<file>`.

## Build

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
  -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=70 -DGGML_CUDA_FA=ON -DGGML_CUDA_GRAPHS=ON \
  -DGGML_CUDA_NCCL=ON -DNCCL_INCLUDE_DIR=/path/to/nccl/include -DNCCL_LIBRARY=/path/to/nccl/lib/libnccl.so.2
cmake --build build -j --target llama-server llama-quantize
```

Multi-GPU tensor parallelism needs NCCL; use GCC 12 or newer. Every push to GitHub is build-checked for sm_70; releases include prebuilt x86_64 Linux binaries (CUDA 12, see the Releases page). For POWER9 and other platforms, build with the commands above.

## Launch parameters

On the AC922, `numactl --membind=0,8` restricts host memory to the two CPU nodes (GPU memory is onlined as NUMA nodes; without it, page cache may occupy VRAM; find the node ids with `numactl --hardware`: the nodes that have CPUs are host memory, usually 0 and 8 on an AC922; x86 machines do not need this prefix); on other machines check node numbers with `numactl -H`; plain x86 servers drop this part. What each parameter does and its impact are in the parameter table in the last section.

### A. 6 GPUs, context 262144 (used for the measurements on this page)

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5 numactl --membind=0,8 ./build/bin/llama-server \
  -m ./models/Qwen3.8-27B-Q8_0.gguf -ngl 999 \
  --split-mode tensor --tensor-split 1,1,1,1,1,1 \
  -c 262144 -np 1 -fa on -ctk q8_0 -ctv q8_0 -b 2048 -ub 2048 \
  --model-draft ./models/Qwen3.8-27B-DFlash2-F16.gguf \
  --spec-type draft-dflash --spec-draft-n-max 7 \
  --host 127.0.0.1 --port 8080 --metrics
```

### B. 4 GPUs, context 262144

Command A with `--tensor-split 1,1,1,1` and a different `CUDA_VISIBLE_DEVICES`: `0,1,3,4` on the AC922 (two GPUs per CPU); `0,1,2,3` on x86, without the `numactl` part. Everything else stays the same.

### Variations on A / B

- **Context 524288 (YaRN)**: `-c 524288`, plus `--rope-scaling yarn --rope-scale 2 --yarn-orig-ctx 262144 --override-kv qwen35.context_length=int:524288`; the YaRN setting applies to all lengths.
- **Concurrency**: `-np N`, context per slot = `-c` ÷ N (e.g. 4 GPUs with `-c 262144 -np 2` gives 131072 per slot; for two slots of 262144 on 6 GPUs, use the 524288 settings plus `-np 2`). Prompt processing is queued in order, so later slots wait for earlier prompts before their first token, and the total time to finish everything is about the same as processing one by one; the benefit is that a request already decoding is not blocked by a later long prompt. Raising `--prefill-pace` (default 30; 0 or 100 = no limit) gives later requests a faster first token and slows down requests that are decoding. A single agent that needs the full long context should still use `-np 1`.
- **Multimodal**: add `--mmproj ./models/mmproj-F16.gguf`, and for video also `--video-ffmpeg-dir <ffmpeg directory>`. Requests go to the OpenAI-compatible `/v1/chat/completions`: images as `image_url`, video as `input_video` (or `video_url`; 4 frames per second by default); PDFs are sent as one rendered image per page by the client. The vision module is split by layer across all GPUs used by the main model by default; when VRAM is short, `--no-mmproj-offload` puts it on the CPU (images and video become much slower), or `-mmdev <device>` puts it on one GPU.
- **Other GPU counts**: change `CUDA_VISIBLE_DEVICES` and `--tensor-split` (one 1 per GPU); the maximum context per GPU count is in the decision steps.
- **Q4 configuration**: `-m ./models/Qwen3.8-27B-UD-Q4_K_M.gguf -ctk q4_0 -ctv q4_0`. 2 GPUs require the Q4 configuration (the Q8_0 main model does not fit on two 16 GB GPUs); at 262144 on 2 GPUs, switch the draft to `./models/Qwen3.8-27B-DFlash2-Q4_K_M.gguf`.
- **Sampling**: the model card recommends temperature 1.0, top_p 0.95, top_k 20, min_p 0 for thinking mode (`--temp 1.0 --top-p 0.95 --top-k 20 --min-p 0`), and temperature 0.7, top_p 0.8, top_k 20, presence_penalty 1.5 for non-thinking mode (`--temp 0.7 --top-p 0.8 --top-k 20 --presence-penalty 1.5 --chat-template-kwargs '{"enable_thinking":false}'`). Append them to the command as server defaults; sampling parameters in a request take precedence. With `top_k ≤ 64` and only top-k, top-p, min-p, temperature and repeat/presence/frequency penalties, top-k candidates are taken on the device (candidates = `top_k` + tokens in the penalty window, at most 256); with DRY or other samplers, or a larger `top_k`, sampling runs on the host over the full vocabulary.

## Docker

The image contains sm_70 (V100) code only, is based on CUDA 12.4.1, and includes NCCL, ffmpeg (video input), numactl and `llama-quantize`; the host needs NVIDIA driver 550 or newer. It is published on the GitHub Container Registry; one tag covers linux/amd64 (x86_64 + V100, NVIDIA Container Toolkit with `--gpus all`) and linux/ppc64le (IBM Power AC922 only, a CDI spec generated by `.devops/v100-ac922-cdi.sh` with `--device nvidia.com/gpu=all`), and `docker pull` picks the host architecture. The entry point is `llama-server`; arguments after the image name go straight to it (with paths changed to `/models/...` inside the container).

### C. Docker, 6 GPUs, AC922 (podman; `podman-docker` provides a `docker` command of the same name)

```bash
sudo dnf install -y podman podman-docker
sudo bash .devops/v100-ac922-cdi.sh        # generates /etc/cdi/nvidia.yaml; run once, and again after driver upgrades
docker run -d --name llama-v100 --device nvidia.com/gpu=all --ipc=host --ulimit memlock=-1 \
  -e LLAMA_NUMA_MEMBIND=0,8 \
  -p 8080:8080 -v <model dir>:/models \
  ghcr.io/1115714829/llama.cpp-v100:2.0.1 \
  -m /models/Qwen3.8-27B-Q8_0.gguf -ngl 999 \
  --split-mode tensor --tensor-split 1,1,1,1,1,1 \
  -c 262144 -np 1 -fa on -ctk q8_0 -ctv q8_0 -b 2048 -ub 2048 \
  --model-draft /models/Qwen3.8-27B-DFlash2-F16.gguf \
  --spec-type draft-dflash --spec-draft-n-max 7 \
  --port 8080
```

### D. Docker, 4 GPUs, x86

```bash
docker run -d --name llama-v100 --gpus all --ipc=host --ulimit memlock=-1 \
  -p 8080:8080 -v <model dir>:/models \
  ghcr.io/1115714829/llama.cpp-v100:2.0.1 \
  -m /models/Qwen3.8-27B-Q8_0.gguf -ngl 999 \
  --split-mode tensor --tensor-split 1,1,1,1 \
  -c 262144 -np 1 -fa on -ctk q8_0 -ctv q8_0 -b 2048 -ub 2048 \
  --model-draft /models/Qwen3.8-27B-DFlash2-F16.gguf \
  --spec-type draft-dflash --spec-draft-n-max 7 \
  --port 8080
```

The draft can also be converted to F16 with the `llama-quantize` inside the image:

```bash
docker run --rm --entrypoint /app/llama-quantize -v <model dir>:/models ghcr.io/1115714829/llama.cpp-v100:2.0.1 \
  /models/Qwen3.8-27B-DFlash2-BF16.gguf /models/Qwen3.8-27B-DFlash2-F16.gguf F16
```

- Use an absolute path for `<model dir>`; `--ipc=host` and `--ulimit memlock=-1` provide the shared memory and pinned memory that multi-GPU communication needs. To use only some GPUs, write `--gpus '"device=0,1"'` on x86 or `--device nvidia.com/gpu=0` etc. on the AC922; use the Q4 configuration on 2 GPUs.
- `-e LLAMA_NUMA_MEMBIND=<nodes>` makes the container start under `numactl --membind=<nodes>`; use it only on machines that online GPU memory as NUMA nodes, such as the AC922 (the nodes with CPUs, `0,8`). The nodes must exist in `numactl --hardware`, otherwise the container exits at startup. Do not restrict memory nodes with `--cpuset-mems` (CUDA initialization fails inside the container).
- The image sets `LLAMA_ARG_HOST=0.0.0.0` by default; whether the server is reachable from outside is decided by `-p` or `--network host`. For external use, add `--api-key-file /run/llama.apikey` and mount `-v <key file>:/run/llama.apikey:ro`. For video input, add `--video-ffmpeg-dir /opt/tools/bin` (the ffmpeg in the image).
- Without access to ghcr.io, download the image file from the Releases page (`llama.cpp-v100-server-<version>-<arch>.tar.gz`) and import it with `docker load -i <file>`, or build it from the source tree: `docker build -f .devops/v100-cuda.Dockerfile -t llama.cpp-v100:server .`.

## Quick deployment (for AI assistants and beginners)

You can hand this whole page to an AI assistant: pick command A–D with the decision steps below (see "Launch parameters" and "Docker"), replace the model paths with the actual directory, then adjust with the parameter table and the symptom table. The numbers in the tables were measured on 1.x on the standard test machine (27B has the same features as in 1.1.1; details in the [1.1.1 README](https://github.com/1115714829/llama.cpp-v100/blob/v100-1.1.1/README.md#测试数据), Chinese).

### Decision steps

```text
Step 1: how many 16 GB V100s? (maximum context measured on 1.x)
  6 GPUs        → command A; Q8 up to 524288 (with YaRN)
  5 GPUs        → command A with CUDA_VISIBLE_DEVICES=0,1,2,3,4 and --tensor-split 1,1,1,1,1; Q8 up to 524288
  4 GPUs        → command B; Q8 up to 262144; Q4 configuration up to 524288
  3 GPUs        → command B changed to 3 GPUs; Q8 up to 131072 (-c 131072); Q4 configuration up to 524288
  2 GPUs        → Q4 configuration only (the ~29 GB Q8_0 main model does not fit); at 262144 switch the draft to DFlash2 Q4_K_M, F16 draft up to 131072
  32 GB GPUs    → not tested; start from the command for the same GPU count
Step 2: images, PDFs or video?
  yes           → add --mmproj (and --video-ffmpeg-dir for video); if VRAM is short, --no-mmproj-offload (images and video much slower)
  no            → omit
Step 3: context beyond 262144?
  yes           → -c 524288 plus the four YaRN parameters (output quality above 262144 not tested)
  no            → -c 262144 or smaller
Step 4: several clients at the same time?
  yes           → -np N, context per slot = -c ÷ N; a single agent that needs the full long context still uses -np 1
  no            → -np 1
Step 5: IBM AC922 (GPU memory onlined into system memory)?
  yes           → prefix numactl --membind=<CPU nodes> (usually 0,8); with Docker use command C (-e LLAMA_NUMA_MEMBIND=0,8)
  no            → no numactl and no LLAMA_NUMA_MEMBIND; with Docker use command D
Step 6: VRAM tight, startup fails?
  try in order  → smaller -c → Q4_K_M draft → Q4 configuration (-m UD-Q4_K_M, -ctk q4_0 -ctv q4_0)
```

### Symptoms and fixes

| Symptom | Check first | Fix |
|---|---|---|
| Out of VRAM at startup | AC922: whether page cache has landed in GPU memory nodes (see the last row); other processes on the GPUs; whether GPU count and context exceed the limits in step 1 | Smaller `-c`; Q4_K_M draft; Q4 configuration; keep `-ub` at 2048; for the vision module use `--no-mmproj-offload` or `-mmdev` |
| Slow decode | Sampling settings (`top_k` above 64, DRY, etc.); temperature; several slots | With `top_k ≤ 64` and only top-k, top-p, min-p, temperature and penalties, sampling runs on the device; acceptance is naturally lower above temperature 0; per-slot decode is naturally lower with several slots, and a smaller `--prefill-pace` speeds up requests that are decoding |
| Slow first token for later requests with several slots | — | Prompt processing is queued in order, so later slots wait for earlier prompts; a larger `--prefill-pace` gives later requests a faster first token |
| Low draft acceptance | Temperature; draft quantization; context length | F16 draft accepts more on short tasks; long context naturally yields fewer tokens per round (4 GPUs, F16: short tasks 3.23, 128K 2.46 tokens / round) |
| Image / video request errors | Whether `--mmproj` is set; whether ffmpeg can be found for video; whether PDFs were converted to images | Add `--mmproj`; add `--video-ffmpeg-dir` for video; the client renders each PDF page to an image; with `-c 1048576 -np 2` the image compute buffer cannot get VRAM, use `--no-mmproj-offload` |
| Log shows `llama_params_fit is not implemented for SPLIT_MODE_TENSOR` | — | A warning: tensor split does not go through the startup VRAM planning and starts with the parameters given; can be ignored |
| VRAM mysteriously occupied on the AC922, out of VRAM after loading the model | In `numactl --hardware`, the nodes without CPUs are GPU memory; check whether their free memory shrank | Start with `numactl --membind=0,8`; wrap downloads and copies of large files in it too; clear page cache that already landed there as root with `sync; echo 1 > /proc/sys/vm/drop_caches` |
