# Qwen3.8-27B (dense model) + DFlash2

[简体中文](27b.md) | **English** | [← Home README](../../README.en.md) | [AI deployment guide](ai-deploy.en.md) | [27B dense model](27b.en.md) | [Qwen3.8-Flash-Next](moe-2.0.0.en.md) | [Benchmark history](benchmarks.en.md) | [Changelog](../../CHANGELOG.en.md)

This page explains how to run Qwen3.8-27B with DFlash2 speculative decoding on V100: model download, build, launch commands and Docker. If you have not chosen a configuration yet, first decide with the [AI deployment guide](ai-deploy.en.md). 27B has the same features as in 1.1.1.

---

## Measured results

Current version 2.0.1.1: 6 × V100-16GB, Q8_0 + DFlash2 F16, context 262144; on ~200K tokens of real code, prefill 2187 tok/s and decode 124.5 tok/s; on ~16K tokens, prefill 2786 tok/s and decode 152.7 tok/s (temperature 0, thinking off, a fresh server, no prefix cache hit). No regression in a same-session A/B comparison with 2.0.1; the temperature-0 output is the same, and the VRAM per GPU is the same.

- Other configurations (4 GPUs, 2/3/5 GPUs and Q4 configurations, `-ub` comparison, 524288 context, concurrency, multimodal) were last measured in full on 1.1.1; see the [1.1.1 results archive](27b-results-1.1.1.en.md).
- Test conditions and all data of every version are in [Benchmark history](benchmarks.en.md#2011).

The draft model is only published as BF16, Q8_0 and Q4_K_M GGUF; the recommended F16 (V100 has no BF16 hardware support) must be converted once with the `llama-quantize` built from this project. Build first (next section), then download and convert with one command:

```bash
scripts/v100-get-models.sh            # downloads from ModelScope to ./models by default
scripts/v100-get-models.sh -s hf      # use Hugging Face instead
```

The script downloads the target and draft models (resumable; files already present are skipped), then converts the draft to `Qwen3.8-27B-DFlash2-F16.gguf`; `-d` sets the model directory, `-q` the path to `llama-quantize`, `-h` shows usage. The vision module is not in the script; download it separately when needed. If you already have the files, only convert: `./build/bin/llama-quantize Qwen3.8-27B-DFlash2-BF16.gguf Qwen3.8-27B-DFlash2-F16.gguf F16`. Single files can also be fetched resumably from a ModelScope direct link: `wget -c https://modelscope.cn/models/<repo>/resolve/master/<file>`.

## Build

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
  -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=70 -DGGML_CUDA_FA=ON -DGGML_CUDA_GRAPHS=ON \
  -DGGML_CUDA_NCCL=ON -DNCCL_INCLUDE_DIR=/path/to/nccl/include -DNCCL_LIBRARY=/path/to/nccl/lib/libnccl.so.2
cmake --build build -j --target llama-server llama-quantize
```

Multi-GPU tensor parallelism needs NCCL; use GCC 12 or newer. The web UI ships with the source (`tools/ui/dist`) and is embedded directly into the program at build time; the whole build needs neither network access nor Node.js; the UI only has to be rebuilt if you change its source, see [AI deployment guide · Build options](ai-deploy.en.md#build-options-when-building-yourself). Every push to GitHub is build-checked for sm_70; releases include prebuilt x86_64 Linux binaries (CUDA 12, see the Releases page). For POWER9 and other platforms, build with the commands above.

## Launch parameters

On the AC922, `numactl --membind=0,8` restricts host memory to the NUMA nodes that have CPUs (the AC922 merges GPU memory into system memory, and without the restriction page cache may occupy VRAM; find the node ids with `numactl --hardware`: the nodes that have CPUs are the host memory nodes); plain x86 servers drop this part. What each parameter does and how to choose it is in [AI deployment guide · Parameters](ai-deploy.en.md#4-parameter-reference).

### A. 6 GPUs, context 262144

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5 numactl --membind=0,8 ./build/bin/llama-server \
  -m ./models/Qwen3.8-27B-Q8_0.gguf -ngl 999 \
  --split-mode tensor --tensor-split 1,1,1,1,1,1 \
  -c 262144 -np 1 -fa on -ctk q8_0 -ctv q8_0 -b 2048 -ub 2048 \
  --model-draft ./models/Qwen3.8-27B-DFlash2-F16.gguf \
  --spec-type draft-dflash --spec-draft-n-max 7 \
  --host 127.0.0.1 --port 8080 --metrics
```

### B. 4 GPUs, context 262144

Command A with `--tensor-split 1,1,1,1` and a different `CUDA_VISIBLE_DEVICES`: `0,1,3,4` on the AC922 (two GPUs per CPU); `0,1,2,3` on x86, without the `numactl` part. Everything else stays the same.

### Variations on A / B

- **Context 524288 (YaRN)**: `-c 524288`, plus `--rope-scaling yarn --rope-scale 2 --yarn-orig-ctx 262144 --override-kv qwen35.context_length=int:524288`; the YaRN setting applies to all lengths.
- **Concurrency**: `-np N`, context per slot = `-c` ÷ N (e.g. 4 GPUs with `-c 262144 -np 2` gives 131072 per slot; for two slots of 262144 on 6 GPUs, use the 524288 settings plus `-np 2`). Prompt processing is queued in order, so later slots wait for earlier prompts before their first token, and the total time to finish everything is about the same as processing one by one; the benefit is that a request already decoding is not blocked by a later long prompt. Raising `--prefill-pace` (default 30; 0 or 100 = no limit) gives later requests a faster first token and slows down requests that are decoding. A single agent that needs the full long context should still use `-np 1`.
- **Multimodal**: add `--mmproj ./models/mmproj-F16.gguf`, and for video also `--video-ffmpeg-dir <ffmpeg directory>`. Requests go to the OpenAI-compatible `/v1/chat/completions`: images as `image_url`, video as `input_video` (or `video_url`; 4 frames per second by default); PDFs are sent as one rendered image per page by the client. The vision module is split across all GPUs used by the main model by default; when VRAM is short, `--no-mmproj-offload` puts it on the CPU (images and video become much slower), or `-mmdev <device>` puts it on one GPU.
- **Other GPU counts**: change `CUDA_VISIBLE_DEVICES` and `--tensor-split` (one 1 per GPU); the maximum context each GPU count can reach is in [AI deployment guide · Choose a model and configuration](ai-deploy.en.md#2-choose-a-model-and-configuration).
- **Q4 configuration**: `-m ./models/Qwen3.8-27B-UD-Q4_K_M.gguf -ctk q4_0 -ctv q4_0`. 2 GPUs require the Q4 configuration (the Q8_0 main model does not fit on 2 × 16 GB GPUs); at 262144 on 2 GPUs, switch the draft to `./models/Qwen3.8-27B-DFlash2-Q4_K_M.gguf`.
- **Sampling**: the model card recommends temperature 1.0, top_p 0.95, top_k 20, min_p 0 for thinking mode (`--temp 1.0 --top-p 0.95 --top-k 20 --min-p 0`), and temperature 0.7, top_p 0.8, top_k 20, presence_penalty 1.5 for non-thinking mode (`--temp 0.7 --top-p 0.8 --top-k 20 --presence-penalty 1.5 --chat-template-kwargs '{"enable_thinking":false}'`). Append them to the command as server defaults; sampling parameters in a request take precedence. Speed is highest when `top_k` is no more than 64 and only top-k, top-p, min-p, temperature and repeat / presence / frequency penalty are used; with DRY or other samplers, or a larger `top_k`, decode becomes slower.

## Docker

The image contains sm_70 (V100) code only, is based on CUDA 12.4.1, and includes NCCL, ffmpeg (video input), numactl and `llama-quantize`; the host needs NVIDIA driver 550 or newer. It is published on the GitHub Container Registry; one tag covers linux/amd64 (x86_64 + V100, NVIDIA Container Toolkit with `--gpus all`) and linux/ppc64le (IBM Power AC922 only, a CDI spec generated by `.devops/v100-ac922-cdi.sh` with `--device nvidia.com/gpu=all`), and `docker pull` picks the host architecture. The entry point is `llama-server`; arguments after the image name go straight to it (with paths changed to `/models/...` inside the container).

### C. Docker, 6 GPUs, AC922 (podman; `podman-docker` provides a `docker` command of the same name)

```bash
sudo dnf install -y podman podman-docker
sudo bash .devops/v100-ac922-cdi.sh        # generates /etc/cdi/nvidia.yaml; run once, and again after driver upgrades
docker run -d --name llama-v100 --device nvidia.com/gpu=all --ipc=host --ulimit memlock=-1 \
  -e LLAMA_NUMA_MEMBIND=0,8 \
  -p 8080:8080 -v <model dir>:/models \
  ghcr.io/1115714829/llama.cpp-v100:2.0.1.1 \
  -m /models/Qwen3.8-27B-Q8_0.gguf -ngl 999 \
  --split-mode tensor --tensor-split 1,1,1,1,1,1 \
  -c 262144 -np 1 -fa on -ctk q8_0 -ctv q8_0 -b 2048 -ub 2048 \
  --model-draft /models/Qwen3.8-27B-DFlash2-F16.gguf \
  --spec-type draft-dflash --spec-draft-n-max 7 \
  --port 8080
```

### D. Docker, 4 GPUs, x86

```bash
docker run -d --name llama-v100 --gpus all --ipc=host --ulimit memlock=-1 \
  -p 8080:8080 -v <model dir>:/models \
  ghcr.io/1115714829/llama.cpp-v100:2.0.1.1 \
  -m /models/Qwen3.8-27B-Q8_0.gguf -ngl 999 \
  --split-mode tensor --tensor-split 1,1,1,1 \
  -c 262144 -np 1 -fa on -ctk q8_0 -ctv q8_0 -b 2048 -ub 2048 \
  --model-draft /models/Qwen3.8-27B-DFlash2-F16.gguf \
  --spec-type draft-dflash --spec-draft-n-max 7 \
  --port 8080
```

The draft can also be converted to F16 with the `llama-quantize` inside the image:

```bash
docker run --rm --entrypoint /app/llama-quantize -v <model dir>:/models ghcr.io/1115714829/llama.cpp-v100:2.0.1.1 \
  /models/Qwen3.8-27B-DFlash2-BF16.gguf /models/Qwen3.8-27B-DFlash2-F16.gguf F16
```

- Use an absolute path for `<model dir>`; `--ipc=host` and `--ulimit memlock=-1` are the shared-memory and pinned-memory settings that multi-GPU runs need. To use only some GPUs, write `--gpus '"device=0,1"'` on x86 or `--device nvidia.com/gpu=0` etc. on the AC922; use the Q4 configuration on 2 GPUs.
- `-e LLAMA_NUMA_MEMBIND=<nodes>` makes the container start under `numactl --membind=<nodes>`; use it only on machines that online GPU memory as NUMA nodes, such as the AC922 (the nodes with CPUs, `0,8`). The nodes must exist in `numactl --hardware`, otherwise the container exits at startup. Do not restrict memory nodes with `--cpuset-mems` (CUDA initialization fails inside the container).
- The image sets `LLAMA_ARG_HOST=0.0.0.0` by default; whether the server is reachable from outside is decided by `-p` or `--network host`. For external use, add `--api-key-file /run/llama.apikey` and mount `-v <key file>:/run/llama.apikey:ro`. For video input, add `--video-ffmpeg-dir /opt/tools/bin` (the ffmpeg in the image).
- Without access to ghcr.io, download the image file from the Releases page (`llama.cpp-v100-server-<version>-<arch>.tar.gz`) and import it with `docker load -i <file>`, or build it from the source tree: `docker build -f .devops/v100-cuda.Dockerfile -t llama.cpp-v100:server .`.
